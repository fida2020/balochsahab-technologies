Not every website needs a database, a server or a content management system. A company site, a product page or a portfolio is mostly the same content for every visitor, and serving it as plain HTML files makes it fast, cheap and hard to break. Our own site, balochsahab.com, works this way: static HTML generated by a small script, hosted on GitHub Pages, with Cloudflare in front.

This guide explains the setup step by step, along with the details that tend to trip people up.

## Why static hosting works well

A static site is a folder of HTML, CSS, JavaScript and image files. The host simply sends those files to the browser. That brings real advantages:

- **Speed.** There is no page to assemble on the server for each visit, and files cache well on a CDN.
- **Security.** With no server-side code, database or admin login, there is far less to attack or keep patched.
- **Cost.** GitHub Pages is free for public repositories, and Cloudflare has a free plan.
- **History.** Every change is a git commit, so you can see who changed what and undo any mistake.

The trade-off is that dynamic features such as forms, search or user accounts need an external service or a separate backend. For a contact form, a form delivery service that forwards submissions to email is usually enough.

## Step 1: Put the site in a GitHub repository

Create a repository and add your site files, with `index.html` at the root (or in a `docs` folder if you prefer). Then, in the repository's **Settings, Pages** section, choose to deploy from a branch, select your main branch and the folder. GitHub builds and publishes the site, usually within a couple of minutes, at an address like `username.github.io/repository`.

Add a `404.html` file at the root; GitHub Pages serves it automatically for missing pages.

## Step 2: Connect your custom domain

In the same Pages settings, enter your custom domain, for example `example.com`. GitHub stores it in a file called `CNAME` at the root of the publishing folder, containing just the domain name. Keep that file in the repository; if a build process deletes it, the custom domain stops working.

Next, set the DNS records at your DNS provider. For an apex domain (no `www`), GitHub's documentation lists a set of A records (and AAAA records for IPv6) pointing to GitHub Pages servers. For `www`, add a CNAME record pointing to `username.github.io`. GitHub recommends verifying your domain in your account settings too, which prevents someone else from claiming it on Pages. Because the exact IP addresses can change, copy them from the [GitHub Pages documentation](https://docs.github.com/en/pages) rather than from a blog post.

## Step 3: Put Cloudflare in front

To use Cloudflare, add your domain to a Cloudflare account and change the domain's nameservers at your registrar to the ones Cloudflare gives you. Then recreate the GitHub DNS records inside Cloudflare's DNS settings.

Each record has a proxy toggle. With the orange cloud on (proxied), traffic goes through Cloudflare's network, gaining its caching, compression and protection. With it off (DNS only), Cloudflare just answers DNS queries.

A practical order that avoids certificate trouble:

1. Add the records in Cloudflare with the proxy **off** at first.
2. Wait for GitHub Pages to issue its HTTPS certificate for your domain, then tick **Enforce HTTPS** in the Pages settings.
3. Turn the Cloudflare proxy **on**.

## Step 4: Get HTTPS right

With Cloudflare proxying, there are two connections: visitor to Cloudflare, and Cloudflare to GitHub. Cloudflare's SSL/TLS encryption mode controls the second.

- **Flexible** sends traffic from Cloudflare to the origin unencrypted. Combined with GitHub's HTTPS enforcement, this can cause an endless redirect loop. Avoid it.
- **Full** or **Full (strict)** encrypts both connections. Since GitHub Pages provides a valid certificate for your domain, Full (strict) is the best choice once that certificate exists.

Also turn on Cloudflare's "Always Use HTTPS" so visitors who type `http://` are redirected.

## Step 5: Caching and cache busting

Cloudflare caches static files such as CSS, JavaScript and images at its edge locations by default. HTML is generally not cached by default, which suits a site that changes occasionally.

The classic problem is a visitor seeing an old stylesheet after you update it. The reliable fix is to change the file's URL whenever its content changes, for example by adding a short hash of the file's contents as a query string. Your build script can compute this automatically:

```html
<link rel="stylesheet" href="/assets/css/style.css?v=3f2a91c0">
```

When the stylesheet changes, the hash changes, the URL is new, and every browser and cache fetches the fresh file. You rarely need to purge Cloudflare's cache manually.

## Step 6: Watch out for Rocket Loader

Cloudflare offers an optimisation called Rocket Loader, which delays and rewrites how JavaScript loads to speed up rendering. It can interfere with third-party scripts that expect to run in their normal order, such as advertising or analytics tags. If you use it, you can exclude a specific script by adding the attribute `data-cfasync="false"` to its script tag, which tells Rocket Loader to leave that script alone:

```html
<script async data-cfasync="false" src="https://example.com/vendor-script.js"></script>
```

If something breaks after enabling an optimisation, disable it first and test again before debugging anything else.

## Step 7: Generate pages with a small build script

Hand-editing the same header and footer in a dozen HTML files leads to mistakes. We keep page content and shared layout in a few source files and run a small Node.js script with no dependencies that writes every HTML page, plus `sitemap.xml` and `robots.txt`. It also validates the content and refuses to build if something is wrong, such as a missing image or a duplicate page title.

A companion test script checks the output: that every internal link resolves, every page has one heading, a title, a meta description and a canonical URL, and the sitemap lists exactly the indexable pages. A GitHub Actions workflow runs both on every push, so mistakes are caught before visitors see them. You do not need a big framework to get these benefits; a few hundred lines of script go a long way.

## Step 8: Sitemap and robots.txt

A `robots.txt` file at the root tells crawlers what they may crawl and where your sitemap is. A `sitemap.xml` lists the canonical address of every page you want indexed. Generate both from the same list of pages your build uses, so they never drift out of date. Then submit the sitemap in [Google Search Console](https://search.google.com/search-console/about) after verifying your domain.

## Step 9: Rolling back

Because every change is a commit, undoing a bad change is simple. Use `git revert` on the commit that caused the problem and push. This creates a new commit that reverses it, keeping history intact and avoiding force-pushes. Before a large redesign, create a git tag on the last good version, so you can always find and restore it.

```bash
git tag backup-before-redesign
git push origin backup-before-redesign
git revert --no-edit abc1234
git push origin main
```

## Conclusion

GitHub Pages with Cloudflare is a dependable, low-cost home for a company website. Set up the domain and DNS carefully, use Full (strict) encryption, version your asset URLs, be cautious with script optimisations, and generate pages, sitemap and robots.txt from one source with automated checks. The result is a site that loads quickly, rarely breaks, and can always be rolled back.
